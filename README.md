# ECQL: DSL Query Generator

Домашнее задание «DSL Query Generator», курс «LLM-инженер».

По заданию описывались правилам= вымышленного корпоративного языка запросов ECQL, который используется в компании «E-Corp».
Основные сущности: [EMPLOYEES], [PROJECTS], [INVENTORY], [DEALS] и поля них вроде: @salary, @status, @city

Корпоративная БД про работников - это скучно и не интересно. Сохранил правила языка но предметную область взял: путеводитель по местам и городам КавМинВод.

Вместо вымышленной компании — места, отзывы, соседство объектов и цены проезда.

# Схема данных

`[PLACES]`
- `@name` — Нарзанная галерея, Провал, Курортный парк, Краеведческий музей
- `@city` — Кисловодск, Пятигорск, Ессентуки, Минеральные Воды, Железноводск, Иноземцево, Лермонтов, вне городов
- `@category` — culture, food, shopping, lodging, nature, service, water, activity, transport
- `@price_rub` — 200, 300, 500, 1300
- `@price_kind` — average_check, per_night
- `@object_kind` — monument, ensemble, heritage_site
- `@heritage_status` — federal, regional, local
- `@wheelchair` — yes, no, limited

`[REVIEWS]`
- `@name` — Жемчужина, Hotel Verona, Espero, Особняк
- `@city` — Кисловодск, Пятигорск, Ессентуки, Железноводск
- `@object_class` — hotel, guesthouse, sanatorium, hostel
- `@rating` — 1, 2, 3, 4, 5
- `@aspects` — номер, расположение, завтрак, персонал, чистота, бассейн и спа, цена, шум, wi-fi, парковка; от одного до четырёх значений через запятую, фильтр через `CONTAINS`

`[PROXIMITY]`
- `@name` — имя объекта-якоря; производное от `[PLACES]` по `place_id`
- `@neighbour_category` — те же значения, что у `@category`
- `@distance_m` — 86, 104, 500, 1500

`[FARES]`
- `@transport` — plane, bus, train, tram
- `@route_start` — Минеральные Воды, Кисловодск, Пятигорск, Москва
- `@route_end` — Москва, Санкт-Петербург, Сочи, Кисловодск
- `@fare_class` — economy, business, platskart, kupe
- `@price_rub` — 30, 35, 8090, 23110

Полная спецификация языка — [docs/dz_ECQL.md](docs/dz_ECQL.md).

# Отличия от правил ДЗ

- Добавлены операторы `CONTAINS` и `NOT CONTAINS` для строковых полей.
- Суффикс вывода (`AS JSON`, `AS TABLE`, `AS LIST`) ставится только тогда, когда
  человек назвал формат словами; иначе не пишется.
- Вложенность спецификацией ДЗ не определена, поэтому сложность выражена числом
  условий от одного до четырёх (через && или ||).
- Правила языка не вводят понятия группировки операций (нет скобок), я не добавлял чтобы не усложнять. Считаю что операторы && и || одновременно запрещены.

# Цепочка сборки

```
csv КМВ (вне проекта) ── vocabulary.py ──▶ vocabulary.json ── planner.py ──▶ slots.json
   ── sheets.py ──▶ *.md ── человек пишет вопросы ──▶ *.md ── builder.py ──▶ jsonl
```

```bash
python -m ecql_dataset.build.planner --vocabulary dataset/ecql/source/vocabulary.json \
    --output dataset/ecql/source/slots.json
    
python -m ecql_dataset.build.sheets --slots dataset/ecql/source/slots.json \
    --directory dataset/ecql/source
    
# сборка jsonl по md файлам:    
python -m ecql_dataset.build.builder --source dataset/ecql/source --output dataset/ecql \
    --vocabulary dataset/ecql/source/vocabulary.json
```

# Как собирался датасет

1. Из csv по КМВ собрал словарь значений: какие есть города, названия, цены, категории.
2. Планировщик разложил слоты - готовые строки ECQL, равномерно покрывающие поля,
   операторы, связки и суффиксы вывода.
3. Claude Code написал под каждый слот вопрос человеческим языком.
4. Билдер собрал jsonl и разложил пары на train, val и test.

## Что вышло после первой генерации

Вопросы получились неестественные: «Плацкартные билеты», «Автобусы дороже тридцати
рублей», «Транспортные объекты - просто назови списком». Именная группа без глагола,
числа прописью, перечень через запятую вместо фразы. Оставил как есть, обучил, посмотрел.

Модель промахнулась на 138 парах из 176 обучающей части. Переписал их, ориентируясь
на промахи прогона, и стало хуже: eval loss 0.258 -> 0.548. Правил только то, на чём
модель ошибалась, и только в train. Проверочная часть осталась в старом стиле, и две
половины датасета разъехались.

## Дополнительный заход: субагент, партии по десять

Взял 85 вопросов val и test и привёл к стилю обучающей части. Отбор сплошной, без
оглядки на ошибки модели: править по промахам то, на чём меряешь, значит подогнать замер.

Партия - десять пар «вопрос и его запрос». Агент возвращает таблицу: править или нет,
класс дефекта, причина, новая формулировка. Файлы он не трогает, правку вносит скрипт -
так строка запроса остаётся нетронутой и пара не уезжает в другой сплит.

Что в промпте агента помогло:

- запрос заморожен, меняется только вопрос, и новый обязан задавать ровно тот же запрос;
- каждое условие запроса названо словами вопроса, лишних условий нет - иначе модель
  учится угадывать;
- до 90 знаков: расписать условие подробнее, чем сказал бы человек, значит облегчить пару;
- на входе список частых зачинов датасета, эти обороты брать нельзя;
- не больше трёх фраз от первого лица на партию, иначе выходит новый штамп вместо старого;
- форма ответа - «списком», «таблицей», «в json» - не всегда в хвосте фразы.

Итог: 80 вопросов переписаны, 5 признаны годными. Инструкция агента целиком -
в `prompt/dataset_editor.md`.
